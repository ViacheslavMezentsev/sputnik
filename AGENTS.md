# AGENTS.md

Правила для ИИ-агентов и участников. С владельцем общаемся на русском; документация ведётся
только на русском.

## Порядок работы

1. Прочитайте [README](README.md), разделы «Текущее состояние» и «Ближайшие шаги»
   в [TODO](TODO.md), затем Unreleased в [CHANGELOG](CHANGELOG.md).
   Известные решения и команды: [HOWTO](HOWTO.md). Требования — в
   [техническом задании](docs/TECHNICAL_SPECIFICATION.md).
2. До изменений проверьте `git status` и существующие правки. Не откатывайте
   и не перезаписывайте чужие незакоммиченные изменения.

## Проект

| Путь | Содержимое |
| :--- | :--- |
| `docs/TECHNICAL_SPECIFICATION.md` | ТЗ; ведётся по навыку `skills/embedded-tech-spec` |
| `boards/` | Профили плат `F411CE`, `H723VG` (TOML для stm32-cmake-yml); позже — `.ioc` и слой платы |
| `modules/` | Git-подмодули с закреплённым коммитом: stm32-cmake, stm32-cmake-yml, stm32-gdbtest |
| `skills/` | Копии навыков из demo-stm32-skills; здесь не правятся ([skills/README.md](skills/README.md)) |

3. Бизнес-логика одна для обеих плат и не зависит от платы: никаких заголовков CMSIS, HAL, LL
   и CubeMX в её исходниках (ТЗ, п. 8.1.2). Различия плат — только в профиле и слое платы.
   Функции «только H723» отключаются при сборке, а не проверкой во время работы (п. 3.3.2).
4. Требования не меняются молча: решение, расходящееся с ТЗ, оформляется новой ревизией ТЗ
   (новый номер, пометки `(р.X.Y)`, вопросы, тест-кейсы, матрица) и проверяется
   `python3 skills/embedded-tech-spec/scripts/check_spec.py --strict docs/TECHNICAL_SPECIFICATION.md`.
   Ссылки на ТЗ из кода — по приложению D ТЗ.
5. Открытые вопросы ТЗ (экран, приёмник, накопитель, кнопки, питание и др.) решает владелец.
   Агент предлагает варианты, но не фиксирует выбор без его решения.
6. Код GPXSee (GPL-3.0) не копируется и не переводится построчно: формат JNX реализуется по
   описанию формата (ТЗ, приложение E). Сторонние библиотеки — только с лицензией, совместимой
   с MIT, с записью в README.
7. Копии навыков в `skills/` не правятся. Изменения вносятся в demo-stm32-skills, затем копии
   обновляются целиком с записью исходного коммита в `skills/README.md`.

## Ветки и слияние

8. Владелец и его агенты работают в ветке `<агент>/<задача>` от свежего main
   (`claude/`, `codex/`, `gemini/`, `dev/`, …). Агент ведёт ветки и коммиты в своём
   клоне `../.work/sputnik` (клонирован по HTTPS), а не в рабочей копии владельца; владелец
   забирает ветку командой `git fetch` (HOWTO). Pull request не используются: ветка,
   перенесённая на свежий main (`git rebase -S origin/main`), сливается перемоткой командой
   `git land` (цикл и псевдоним описаны в HOWTO).
9. Внешние участники присылают изменения через fork и pull request; владелец переносит их
   в main тем же способом, сохраняя линейную историю.
10. Push, `git land`, теги и релизы выполняет владелец. Агент не запускает их без отдельного
    явного поручения. Отправку ветки и её слияние в main агент указывает отдельными шагами;
    слияние допустимо только после успешной проверки CI. Если после проверки ветку пришлось
    перенести на новый main, её отправляют заново и снова дожидаются CI.

## Коммиты

11. Conventional Commits на русском: `feat(gpx): запись трека с завершением после сброса`,
    `docs(тз): ревизия 1.1`; для общих изменений — `docs:`, `ci:`, `chore:`, `build:`.
    Коммит охватывает задачу целиком, а не отдельные файлы.
12. Коммиты подписываются ключом (SSH или GPG), зарегистрированным в GitHub как Signing Key:
    участник — своим ключом, агент — ключом агента `../.work/keys/claude_signing`
    (`gpg.format ssh`) от имени и email владельца. Строка `Co-Authored-By` разрешена;
    `Claude-Session` и другие ссылки на сессии агентов не добавляются.
13. Не коммитьте серийные номера отладчиков, персональные пути, детали конкретного стенда,
    токены и ключи, прошивки HEX/BIN/ELF, логи и записи оборудования, карты и треки (кроме
    маленьких тестовых файлов в `tests/data/`), скачанные утилиты и кэши. Шаблоны — в `.gitignore`.

## Проверки

14. CI не заменяет проверку на плате. В отчёте указывайте, что проверено на плате (профиль,
    модели периферии), что — в эмуляторе, сборкой или только анализом. Не утверждайте того,
    что не запускалось.
15. На плате проверяем DDTT-сценариями stm32-gdbtest по именам из ELF, без тестового кода
    в прошивке (ТЗ, п. 7.11.4, 8.7.3).

## Проведение исследований

Перед исследованием прочитайте локальные правила: `docs/research/README.md` (порядок работы,
имена, журнал `docs/research/HISTORY.md`, песочница `tests/sandbox/`). Файла может не быть —
тогда правил нет, и их стоит согласовать с разработчиком. Обе папки локальные и в Git не
входят.

## Документация и отчёт

16. Новое повторно полезное решение добавляйте в HOWTO вместе с изменением.
    Обновляйте TODO (отметки `[ ]`/`[x]` — по правилу в его начале) и Unreleased в CHANGELOG.
17. После каждого этапа сообщайте результат, ограничения и следующий шаг, текущую ветку
    (проверенную через `git branch --show-current`) и последовательность следующих
    Git-команд: забрать ветку из `.work`, проверить подписи, отправить, дождаться CI,
    при необходимости `git rebase -S origin/main`, `git land`.
