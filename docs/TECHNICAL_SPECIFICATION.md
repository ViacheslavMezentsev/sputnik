## 1. Введение

### 1.1. Назначение документа

1.1.1. Документ определяет требования к прошивке прототипа наручного навигатора «Спутник»: приём GPS/ГЛОНАСС, запись трека в GPX, отображение карты JNX и трека, навигация, анализ трека во время записи и после сохранения.

1.1.2. Документ является основой для реализации и верификации: каждое требование имеет постоянный номер, на который ссылаются комментарии в коде, тесты и матрица прослеживаемости (раздел 12).

### 1.2. Область применения

1.2.1. Требования применимы к прошивке для двух профилей плат: `F411CE` и `H723VG` (раздел 3), к платформонезависимой бизнес-логике и к слою платы.

1.2.2. Документ не описывает: выбор и схемотехнику периферии (экран, приёмник, накопитель, кнопки, питание — до решений по вопросам 13.2.1–13.2.5), корпус и носимость, программы для ПК, подготовку карт JNX. Требования к взаимодействию с ними — в разделе 8.

### 1.3. Метод формирования

1.3.1. Источники: постановка задачи владельцем; README и схемы WeAct для обеих плат; описание формата JNX (п. 1.5.4); исходники GPXSee (п. 1.5.5), прочитанные только для понимания формата; стандарт GPX 1.1 (п. 1.5.1); NMEA 0183 (п. 1.5.2).

1.3.2. Сведения о формате JNX, которые приведены в разделе 5 и приложении B, сверены с порядком чтения в GPXSee. Поля, которые GPXSee не использует (подпись, срок действия, метаданные в конце файла), до реализации сверяются с описанием формата (вопрос 13.2.26).

1.3.3. Целевой реализацией считается код в этом репозитории, который появится на следующих этапах. В случае расхождения между этим документом и кодом расхождение считается дефектом одного из них и разрешается пересмотром ревизии документа.

## 2. Общее описание

### 2.1. Контекст

2.1.1. Прототип — плата WeAct с подключёнными экраном, приёмником GNSS, картой microSD, кнопками и питанием от аккумулятора. Пользователь носит его на руке или в руке во время прогулки, пробежки, велопоездки или похода.

2.1.2. Карты JNX готовятся на ПК сторонними программами и копируются на карту microSD вместе с треками GPX для навигации. Записанные треки забираются с карты microSD и открываются на ПК (GPXSee, Garmin BaseCamp и т. п.).

2.1.3. Прототип служит для проверки архитектуры и выбора периферии. Одна бизнес-логика собирается для двух плат; функции, которые не помещаются в ресурсы STM32F411CE, доступны только на STM32H723VG (п. 3.3).

### 2.2. Функции

2.2.1. Приём и разбор данных приёмника GNSS (GPS и ГЛОНАСС одновременно), отображение состояния спутников и качества решения.

2.2.2. Запись трека в файл GPX 1.1 с паузой, продолжением и защитой от потери данных при пропадании питания.

2.2.3. Отображение растровой карты JNX с текущим положением и треком; переключение уровней детализации и сдвиг карты кнопками.

2.2.4. Навигация: к путевой точке, по загруженному треку или маршруту, обратно по своему треку.

2.2.5. Анализ трека во время записи: расстояние, время, скорость, темп, набор и сброс высоты.

2.2.6. Анализ сохранённого трека: те же показатели, отрезки по расстоянию, профиль высоты.

2.2.7. Отметка путевых точек, настройки, индикация заряда.

### 2.3. Роли и потребители

| Роль | Взаимодействие |
| :--- | :--- |
| Пользователь | Кнопки и экран: запись, карта, навигация, просмотр статистики, настройки |
| Программы на ПК | Читают записанные GPX; готовят JNX и GPX для навигации; файлы передаются через карту microSD (и, возможно, USB — вопрос 13.2.17) |
| Разработчик | Сборка профилей, отладка по SWD, журнал (п. 8.7), DDTT-сценарии |
| CI | Сборка обоих профилей, тесты бизнес-логики на ПК, проверка документов (п. 8.8) |

### 2.4. Границы

2.4.1. Вне области ревизии 1.0: векторные карты (IMG, Mapsforge), прокладка маршрута по дорогам, датчики пульса, беспроводная связь (BLE, Wi-Fi), обновление прошивки без программатора, корпус и влагозащита.

2.4.2. Барометр, магнитометр и акселерометр не входят в ревизию 1.0; решение о включении — вопрос 13.2.16.

### 2.5. Ограничения платформы

2.5.1. STM32F411CE: 128 КиБ RAM не вмещают кадровый буфер экрана 240×240 точек в формате RGB565 (115 200 байт) вместе с остальными данными. На этом профиле изображение формируется полосами или прямо в память экрана (п. 3.4).

2.5.2. STM32H723VG: 564 КиБ RAM разбиты на несколько областей (DTCM, AXI SRAM, SRAM1–SRAM4); размещение буферов по областям выбирается при создании проекта CubeMX.

2.5.3. Порядок байтов обоих MCU — little-endian; это совпадает с порядком байтов JNX (п. 5.1.2).

2.5.4. Наличие аппаратного JPEG-кодека у STM32H723 не подтверждено (вопрос 13.2.6); требования раздела 7 не опираются на него.

| Файловая система (объект ФС, файлы, сектор) | ≈ 2 500 | 3 открытых файла |
| Приём UART GNSS (кольцевой буфер DMA) + строка NMEA | 1 024 + 128 | `NMEA_LINE_MAX` |
| Буфер записи GPX | 2 048 | п. 7.4.8 |
| Маршрут следования | 16 000 | `ROUTE_POINTS_F411` × 8 байт |
| Статистика, состояние, интерфейс | ≈ 4 000 | |
| Стек | 8 192 | уточняется анализом |
| **Итого** | **≈ 50 000** | из 131 072; запас для шрифтов, профиля высоты, кэша индекса тайлов |

## 4. Модель данных

### 4.1. Фикс

4.1.1. Фикс ДОЛЖЕН содержать: время UTC с точностью до миллисекунд, дату; широту и долготу; высоту над уровнем моря (MSL), м; скорость над землёй, м/с; курс над землёй, градусы от истинного севера; тип решения (нет, 2D, 3D, дифференциальное); число используемых спутников по системам (GPS, ГЛОНАСС, прочие); HDOP; признак достоверности каждого поля. `[N]`

4.1.2. Широта и долгота ДОЛЖНЫ храниться целыми числами со знаком в единицах 10⁻⁷ градуса (`int32_t`): диапазон ±1 800 000 000 помещается в тип, шаг около 1,1 см. Причина: целые координаты не теряют точность NMEA и одинаково ведут себя на ПК и на MCU. `[N]`

4.1.3. Отсутствующее в предложениях NMEA поле ДОЛЖНО помечаться недостоверным, а не заменяться нулём. `[N]`

### 4.2. Точка трека

4.2.1. Точка трека ДОЛЖНА содержать: время UTC, широту, долготу (п. 4.1.2), высоту (если достоверна), число спутников, HDOP. `[N]`

### 4.3. Трек и сегмент

4.3.1. Трек ДОЛЖЕН иметь имя, время начала и один или несколько сегментов; сегмент содержит не менее одной точки. `[N]`

4.3.2. Состояние записи ДОЛЖНО принимать значения: `Stopped` (нет записи), `Recording`, `Paused`. Переходы — по п. 7.4.2. `[N]`

### 4.4. Показатели трека

4.4.1. Показатели трека ДОЛЖНЫ включать: общее время, время движения, расстояние, среднюю скорость, среднюю скорость движения, максимальную скорость, средний темп движения, набор и сброс высоты, минимальную и максимальную высоту. Правила расчёта — п. 7.7. `[N]`

### 4.5. Путевая точка

4.5.1. Путевая точка ДОЛЖНА содержать: имя (до `WPT_NAME_MAX` байт UTF-8), время UTC, широту, долготу, высоту (если достоверна). `[N]`

## 5. Формат карт JNX (нормативный для чтения)

### 5.1. Общие правила

5.1.1. Прошивка ДОЛЖНА только читать файлы JNX; запись и изменение JNX вне области. `[N]`

5.1.2. Многобайтовые числа JNX ДОЛЖНЫ читаться как little-endian; координаты — как `int32` со знаком в единицах `JNX_COORD_UNIT`: градусы = значение × 180 / 2 147 483 647 (`0x7FFFFFFF`). `[N]`

5.1.3. Реализация ДОЛЖНА поддерживать версии файла 3 и 4; файл другой версии ДОЛЖЕН отклоняться с кодом `JnxBadVersion` без чтения уровней. `[N]`

5.1.4. Чтение НЕ ДОЛЖНО предполагать, что весь файл, таблица уровней или таблица тайлов помещаются в RAM: доступ к файлу — позиционированием и чтением частей. `[N]`

5.1.5. Реализация ДОЛЖНА быть написана по описанию формата (п. 1.5.4) и этому разделу; код GPXSee НЕ ДОЛЖЕН копироваться или переводиться построчно (приложение E). `[N]`

### 5.2. Заголовок

5.2.1. Заголовок ДОЛЖЕН читаться по таблице (смещения от начала файла); поля, не перечисленные в таблице, при чтении карты не используются. `[N]`

| Смещение | Размер | Поле | Использование |
| :---: | :---: | :--- | :--- |
| `0x00` | 4 | Версия (`uint32`): 3 или 4 | п. 5.1.3 |
| `0x04` | 4 | Серийный номер устройства | не используется |
| `0x08` | 4 | Северная граница карты (`int32`) | п. 5.2.2 |
| `0x0C` | 4 | Восточная граница (`int32`) | п. 5.2.2 |
| `0x10` | 4 | Южная граница (`int32`) | п. 5.2.2 |
| `0x14` | 4 | Западная граница (`int32`) | п. 5.2.2 |
| `0x18` | 4 | Число уровней (`uint32`) | п. 5.2.3 |
| `0x1C` | 20 | Срок действия, идентификатор продукта, CRC, версия и смещение подписи (по описанию, вопрос 13.2.26) | не используется |
| `0x30` | 4 | Z-порядок (`uint32`), только версия 4 | п. 7.5.3 |

5.2.2. Границы ДОЛЖНЫ проверяться: север > юг, восток > запад, широты в пределах ±90°, долготы в пределах ±180°. При нарушении файл отклоняется с кодом `JnxBadBounds`. Карты, пересекающие меридиан 180°, в ревизии 1.0 не поддерживаются (вопрос 13.2.8). `[N]`

5.2.3. Число уровней ДОЛЖНО быть от 1 до `JNX_MAX_LEVELS` включительно; иначе файл отклоняется с кодом `JnxBadLevels`. `[N]`

### 5.3. Таблица уровней

5.3.1. Таблица уровней ДОЛЖНА читаться с смещения `JNX_LEVELS_V3` (`0x30`) для версии 3 и `JNX_LEVELS_V4` (`0x34`) для версии 4. `[N]`

5.3.2. Запись уровня ДОЛЖНА читаться как: число тайлов (`uint32`), смещение таблицы тайлов уровня от начала файла (`uint32`), масштаб (`uint32`). В версии 4 за ними следуют `uint32` (назначение — по описанию, вопрос 13.2.26) и строка авторских прав, завершённая нулевым байтом; длина записи уровня версии 4 переменная. `[N]`

5.3.3. Строка авторских прав ДОЛЖНА читаться до нулевого байта, но не длиннее `JNX_STRING_MAX` байт; более длинная строка обрезается при отображении, чтение продолжается после её нулевого байта. Кодировка строки — вопрос 13.2.26. `[N]`

5.3.4. Уровень ДОЛЖЕН отклоняться (не участвовать в отрисовке, файл остаётся пригодным), если смещение таблицы тайлов плюс число тайлов × `JNX_TILE_ENTRY_SIZE` выходит за размер файла. `[N]`

5.3.5. Порядок уровней в файле ДОЛЖЕН считаться порядком от наименее к наиболее подробному; проверка — по площади первого тайла уровня. Семантика поля «масштаб» — вопрос 13.2.8; до решения выбор уровня опирается на фактическое разрешение (п. 7.5.4), а не на это поле. `[N]`

### 5.4. Таблица тайлов

5.4.1. Запись тайла ДОЛЖНА иметь размер `JNX_TILE_ENTRY_SIZE` = 28 байт и читаться как: север, восток, юг, запад (`int32` по п. 5.1.2); ширина и высота растра в точках (`uint16`); размер данных (`uint32`); смещение данных от начала файла (`uint32`). `[N]`

5.4.2. Тайл ДОЛЖЕН пропускаться (с увеличением счётчика `jnx_bad_tiles`), если размер данных равен нулю, данные выходят за размер файла, ширина или высота равны нулю или больше `TILE_MAX_DIM`, либо границы нарушают правило п. 5.2.2. `[N]`

5.4.3. Пиксели тайла ДОЛЖНЫ сопоставляться координатам линейно по широте и долготе внутри границ тайла (допущение 13.1.1). `[N]`

### 5.5. Данные тайла

5.5.1. Данные тайла — поток JPEG без начального маркера SOI (`0xFF 0xD8`). Декодер ДОЛЖЕН получать поток с восстановленным маркером SOI перед данными тайла, без копирования всего тайла в RAM на `F411CE`. `[N]`

5.5.2. Декодер ДОЛЖЕН поддерживать baseline JPEG (последовательный, Хаффман, 8 бит) с компонентами YCbCr 4:4:4, 4:2:2, 4:2:0 и оттенками серого. `[N]`

5.5.3. Тайл в неподдерживаемом варианте JPEG (прогрессивный, арифметическое кодирование, 12 бит) или с ошибкой декодирования ДОЛЖЕН выводиться заполнителем (п. 7.5.6) с увеличением счётчика `jpeg_errors`; отрисовка остальных тайлов продолжается. `[N]`

### 5.6. Индекс тайлов

5.6.1. Поиск тайлов, пересекающих окно карты, ДОЛЖЕН выполняться за время п. 9.2.4 без чтения всей таблицы тайлов уровня при каждой перерисовке. `[N]`

5.6.2. Для этого прошивка МОЖЕТ строить вспомогательный индекс тайлов на накопителе в каталоге `CACHE_DIR`. Индекс ДОЛЖЕН содержать признаки исходного файла (размер, время изменения, первые 0x34 байт заголовка) и перестраиваться при их несовпадении. `[N]`

5.6.3. Повреждённый или неполный индекс ДОЛЖЕН обнаруживаться (контрольная сумма) и перестраиваться; отказ записи индекса НЕ ДОЛЖЕН мешать отрисовке карты (поиск тогда идёт прямым чтением таблицы тайлов). `[N]`

## 6. Формат записи трека GPX (нормативный)

### 6.1. Структура файла

6.1.1. Файл трека ДОЛЖЕН соответствовать схеме GPX 1.1 (п. 1.5.1): кодировка UTF-8 без BOM, корневой элемент `gpx` с атрибутами `version="1.1"`, `creator`, пространством имён `http://www.topografix.com/GPX/1/1`. `[N]`

6.1.2. Файл ДОЛЖЕН содержать `metadata` со временем начала записи, один элемент `trk` с `name` и одним или несколькими `trkseg`. `[N]`

6.1.3. Атрибут `creator` ДОЛЖЕН содержать имя прошивки, версию и профиль платы, например `sputnik 0.1.0 F411CE`. `[N]`

6.1.4. Путевые точки (`wpt`) НЕ ДОЛЖНЫ записываться в файл трека во время записи: схема требует `wpt` до `trk`. Они сохраняются по п. 7.6.8. `[N]`

### 6.2. Точка трека

6.2.1. Каждая точка ДОЛЖНА записываться элементом `trkpt` с атрибутами `lat` и `lon` в градусах с `GPX_COORD_DECIMALS` = 7 знаками после запятой, вычисленными из целых значений п. 4.1.2 без двоичной плавающей точки (точное десятичное представление). `[N]`

6.2.2. Дочерние элементы точки ДОЛЖНЫ идти в порядке схемы: `ele` (м, 1 знак после запятой; только при достоверной высоте), `time` (ISO 8601, UTC, суффикс `Z`; доли секунды — только если интервал записи меньше 1 с), `sat`, `hdop` (1 знак после запятой). `[N]`

6.2.3. Скорость и курс в ревизии 1.0 в файл не записываются: GPX 1.1 не содержит этих элементов. Запись через расширения — вопрос 13.2.12. `[N]`

### 6.3. Устойчивость к потере питания

6.3.1. После каждого сброса буфера на накопитель (п. 7.4.8) файл ДОЛЖЕН быть корректным документом GPX: за последней записанной точкой следует завершение `</trkseg></trk></gpx>` и перевод строки. Новые точки записываются поверх завершения, после них завершение записывается снова. `[N]`

6.3.2. Восстановление файла, повреждённого при потере питания во время записи, ДОЛЖНО выполняться по п. 7.4.10. `[N]`

### 6.4. Пример (информативно)

```xml
<?xml version="1.0" encoding="UTF-8"?>
<gpx version="1.1" creator="sputnik 0.1.0 F411CE"
     xmlns="http://www.topografix.com/GPX/1/1"
     xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
     xsi:schemaLocation="http://www.topografix.com/GPX/1/1 http://www.topografix.com/GPX/1/1/gpx.xsd">
  <metadata><time>2026-11-09T07:15:02Z</time></metadata>
  <trk>
    <name>20261109-071502</name>
    <trkseg>
      <trkpt lat="56.8389260" lon="60.6057020"><ele>272.4</ele><time>2026-11-09T07:15:02Z</time><sat>11</sat><hdop>0.8</hdop></trkpt>
    </trkseg>
  </trk>
</gpx>
```

## 7. Функциональные требования: жизненный цикл и операции

### 7.1. Запуск

7.1.1. После включения прошивка ДОЛЖНА выполнить шаги строго в следующем порядке: (а) тактирование и периферия платы; (б) экран — заставка с версией и профилем; (в) накопитель и файловая система; (г) настройки (п. 7.12); (д) проверка незавершённого трека (п. 7.4.10); (е) приёмник GNSS; (ж) поиск карт JNX (п. 7.5.2); (з) основной экран. `[N]`

7.1.2. Отказ любого шага (в)–(ж) НЕ ДОЛЖЕН останавливать запуск: функции, зависящие от отказавшего шага, недоступны, причина показывается на экране состояния (п. 7.11.2). `[N]`

7.1.3. Основной экран ДОЛЖЕН появляться не позднее `BOOT_TO_UI_S` после подачи питания при исправном накопителе (без учёта построения индекса тайлов, п. 5.6.2). `[N]`

### 7.2. Приём GNSS

7.2.1. Прошивка ДОЛЖНА принимать поток NMEA 0183 от приёмника через UART с DMA без потери байтов на скорости, выбранной для приёмника (вопрос 13.2.2). `[N]`

7.2.2. Строка NMEA ДОЛЖНА приниматься только при верной контрольной сумме; строки длиннее `NMEA_LINE_MAX` байт и с неверной суммой отбрасываются с увеличением счётчиков `nmea_too_long` и `nmea_bad_checksum`. `[N]`

7.2.3. Прошивка ДОЛЖНА разбирать предложения RMC, GGA, GSA и GSV с любым идентификатором источника из п. 1.5.2; неизвестные предложения пропускаются без ошибки. `[N]`

7.2.4. Фикс ДОЛЖЕН формироваться по завершении эпохи: RMC и GGA с одинаковым временем; фикс с несовпадающим временем не формируется. `[N]`

7.2.5. Если за `GNSS_FIX_TIMEOUT_S` не получено ни одного фикса с достоверными координатами, состояние ДОЛЖНО переходить в «нет решения»; это видно на экране и учитывается записью трека (п. 7.4.6). `[N]`

7.2.6. Экран спутников ДОЛЖЕН показывать число видимых и используемых спутников отдельно для GPS, ГЛОНАСС и прочих систем, тип решения и HDOP. `[N]`

7.2.7. Прошивка ДОЛЖНА настраивать в приёмнике одновременный приём GPS и ГЛОНАСС и частоту решения `NAV_RATE_HZ`, если приёмник это поддерживает; команды настройки зависят от модели (вопрос 13.2.2). `[N]`

### 7.3. Время

7.3.1. Часы реального времени ДОЛЖНЫ устанавливаться по UTC из первого достоверного фикса с датой и затем корректироваться при расхождении более чем на 1 с. `[N]`

7.3.2. Локальное время на экране ДОЛЖНО вычисляться из UTC и смещения из настроек; имена файлов и время в GPX — по UTC (вопрос 13.2.14). `[N]`

### 7.4. Запись трека

7.4.1. Запись ДОЛЖНА управляться действиями «Старт», «Пауза», «Продолжить», «Стоп и сохранить», «Стоп без сохранения» (последнее — с подтверждением). `[N]`

7.4.2. Переходы состояний ДОЛЖНЫ соответствовать таблице; действие, не указанное для состояния, игнорируется. `[N]`

| Состояние | Действие | Новое состояние | Файл |
| :--- | :--- | :--- | :--- |
| `Stopped` | Старт | `Recording` | создаётся (п. 7.4.3) |
| `Recording` | Пауза | `Paused` | буфер сбрасывается |
| `Paused` | Продолжить | `Recording` | новый сегмент |
| `Recording`, `Paused` | Стоп и сохранить | `Stopped` | сбрасывается и закрывается |
| `Recording`, `Paused` | Стоп без сохранения | `Stopped` | закрывается и удаляется |

7.4.3. Файл трека ДОЛЖЕН создаваться в каталоге `TRACK_DIR` с именем по времени начала записи UTC `ГГГГММДД-ЧЧММСС.gpx`; при совпадении имени добавляется суффикс `-1`, `-2` и т. д. `[N]`

7.4.4. Старт без достоверного фикса ДОЛЖЕН быть разрешён: файл создаётся по времени часов; если часы не установлены, имя — `NOTIME-NNNN.gpx` с наименьшим свободным номером. Точки записываются с появлением фикса. `[N]`

7.4.5. В состоянии `Recording` точка ДОЛЖНА записываться не чаще одного раза за интервал `TRACK_INTERVAL_S` (по умолчанию 1 с, настраивается от 1 до 60 с) из последнего фикса с достоверными координатами. Запись по пройденному расстоянию и автопауза — вопрос 13.2.10. `[N]`

7.4.6. Новый сегмент ДОЛЖЕН начинаться после продолжения записи из паузы и после перерыва в фиксах длительностью не менее `TRACK_GAP_S`. `[N]`

7.4.7. Точки с HDOP больше `HDOP_MAX` ДОЛЖНЫ записываться в файл, но не учитываться в расстоянии и скоростях (п. 7.7.3). `[N]`

7.4.8. Точки ДОЛЖНЫ накапливаться в буфере RAM и сбрасываться на накопитель не реже чем раз в `GPX_FLUSH_S`, а также при паузе, остановке и низком заряде (п. 7.10.3). При потере питания теряются только точки после последнего сброса. `[N]`

7.4.9. Отказ записи на накопитель ДОЛЖЕН сохранять состояние `Recording` с накоплением точек в буфере, пока он не заполнится, с повторными попытками и предупреждением на экране; при заполнении буфера новые точки отбрасываются с увеличением счётчика `track_points_lost`. `[N]`

7.4.10. При запуске прошивка ДОЛЖНА проверять файл трека, отмеченный в настройках как незавершённый. Если файл не заканчивается корректным завершением (п. 6.3.1), содержимое после последнего полного `</trkpt>` удаляется и записывается завершение. Пользователю предлагается продолжить этот трек новым сегментом или закрыть его. `[N]`

7.4.11. Заполнение накопителя ДОЛЖНО обнаруживаться заранее: при свободном месте менее `STORAGE_MIN_FREE` запись не стартует, а идущая запись сбрасывает буфер, сохраняет файл и останавливается с сообщением. `[N]`

### 7.5. Карта

7.5.1. Прошивка ДОЛЖНА искать файлы JNX в каталоге `MAP_DIR` при запуске и по команде пользователя; найденные файлы проверяются по разделу 5, отклонённые показываются в списке карт с причиной. Число одновременно используемых файлов — до `JNX_MAX_FILES`. `[N]`

7.5.2. Пользователь ДОЛЖЕН иметь возможность включить или выключить каждую найденную карту; выбор сохраняется в настройках. `[N]`

7.5.3. При перекрытии нескольких включённых карт тайлы ДОЛЖНЫ выводиться в порядке возрастания Z-порядка (версия 4; у версии 3 Z-порядок считается равным 0), при равенстве — в порядке имён файлов; более поздний тайл перекрывает более ранний. `[N]`

7.5.4. Уровень ДОЛЖЕН выбираться так, чтобы разрешение растра (градусов на точку по долготе) было ближайшим к разрешению окна карты при выбранном масштабе, не грубее более чем в 2 раза; если такого уровня нет, берётся ближайший более грубый с увеличением (повтором точек). `[N]`

7.5.5. Масштаб окна карты ДОЛЖЕН переключаться кнопками ступенями, кратными 2; сдвиг карты кнопками — на половину окна. Режим «следовать за положением» включается кнопкой и при начале записи. `[N]`

7.5.6. Область окна без покрытия картой ДОЛЖНА заливаться фоном; тайл с ошибкой (п. 5.5.3) — заполнителем, отличимым от фона. `[N]`

7.5.7. Карта ДОЛЖНА поддерживать ориентацию «север вверху». `[N]`

7.5.8. Только `H723VG`: карта ДОЛЖНА поддерживать ориентацию «по курсу» с поворотом изображения при скорости не менее `MOVING_SPEED_MPS`; ниже этой скорости угол поворота сохраняется. `[N]`

7.5.9. Только `H723VG`: изображение ДОЛЖНО формироваться в кадровом буфере в RAM и выводиться на экран целиком, без видимых промежуточных состояний. `[N]`

7.5.10. Только `H723VG`: сжатые данные недавно прочитанных тайлов ДОЛЖНЫ храниться в кэше RAM объёмом не менее `TILE_CACHE_H723` с вытеснением давно не использованных. `[N]`

7.5.11. Поверх карты ДОЛЖНЫ выводиться: текущий трек, маршрут следования (п. 7.6), путевые точки, отметка положения с направлением движения, масштабная линейка. Только `H723VG`: дополнительно до `OVERLAY_TRACKS_H723` сохранённых треков. `[N]`

7.5.12. При отсутствии карт или при отключённом декодировании (п. 3.3.3) окно карты ДОЛЖНО показывать трек, маршрут, путевые точки и положение на фоне с координатной сеткой. `[N]`

7.5.13. Только `F411CE`: изображение ДОЛЖНО формироваться полосами в буфере не более `STRIP_BYTES_F411` байт либо прямой записью в память экрана. `[N]`

### 7.6. Навигация

7.6.1. Прошивка ДОЛЖНА поддерживать режимы: к путевой точке; по маршруту следования; обратно по текущему треку. Состав режимов — вопрос 13.2.20. `[N]`

7.6.2. Маршрут следования ДОЛЖЕН загружаться из файла GPX в каталоге `ROUTE_DIR`: элементы `trk`/`trkseg`/`trkpt` или `rte`/`rtept` (первый трек или маршрут файла). `[N]`

7.6.3. Загрузка ДОЛЖНА работать при любом размере файла с постоянным расходом RAM; если точек больше предела профиля (`ROUTE_POINTS_F411` или `ROUTE_POINTS_H723`), маршрут прореживается так, чтобы отклонение прореженной линии от исходной не превышало `ROUTE_SIMPLIFY_M`; если это невозможно, загрузка отклоняется с сообщением. `[N]`

7.6.4. В режиме навигации ДОЛЖНЫ показываться: расстояние и азимут до цели (путевой точки или конца маршрута), отклонение от маршрута, расстояние до конца маршрута по линии маршрута, расчётное время прибытия по средней скорости движения. `[N]`

7.6.5. При отклонении от маршрута более чем на `OFF_ROUTE_M` в течение не менее 10 с ДОЛЖНО выдаваться предупреждение (экран и, если есть, звук или вибрация — вопрос 13.2.4). `[N]`

7.6.6. Прибытие ДОЛЖНО фиксироваться при входе в круг радиусом `ARRIVAL_RADIUS_M` вокруг цели. `[N]`

7.6.7. Путевая точка ДОЛЖНА отмечаться одним действием в текущем положении с автоматическим именем `WPT-NNN`. `[N]`

7.6.8. Путевые точки ДОЛЖНЫ сохраняться в файл GPX `WAYPOINTS_FILE` (элементы `wpt`) с перезаписью через временный файл: после потери питания на накопителе остаётся прежний или новый файл целиком. Хранение — вопрос 13.2.20. `[N]`

### 7.7. Анализ трека во время записи

7.7.1. Показатели п. 4.4.1 ДОЛЖНЫ обновляться с каждой записанной точкой и показываться на экране данных. Набор полей экрана — настраиваемый. `[N]`

7.7.2. Расстояние между точками ДОЛЖНО вычисляться по формуле большого круга (гаверсинус) с радиусом `R_EARTH_M`; расхождение с геодезическим расстоянием WGS-84 на отрезках до 10 км — не более 0,5 %. `[N]`

7.7.3. В расстояние и скорости НЕ ДОЛЖНЫ входить: отрезки между сегментами; отрезки к точкам с HDOP больше `HDOP_MAX`; отрезки со скоростью выше `MAX_PLAUSIBLE_SPEED_MPS` (выбросы). `[N]`

7.7.4. Время движения ДОЛЖНО накапливаться на отрезках, где скорость приёмника не ниже `MOVING_SPEED_MPS`. `[N]`

7.7.5. Набор и сброс высоты ДОЛЖНЫ считаться с гистерезисом `ELEV_HYST_M`: изменение учитывается, когда высота отходит от последнего опорного значения не менее чем на эту величину. Источник высоты — приёмник (барометр — вопрос 13.2.16). `[N]`

7.7.6. Максимальная скорость ДОЛЖНА определяться по скорости приёмника, сглаженной скользящим средним за `SPEED_SMOOTH_S`. `[N]`

7.7.7. Пороги п. 7.7.3–7.7.6 — предварительные (вопрос 13.2.11) и ДОЛЖНЫ задаваться константами в одном месте кода. `[N]`

### 7.8. Анализ сохранённого трека

7.8.1. Прошивка ДОЛЖНА показывать список треков в `TRACK_DIR` и для выбранного трека — показатели п. 4.4.1, вычисленные по файлу теми же функциями, что и во время записи. Для трека, записанного прошивкой, расхождение с показателями, видимыми при остановке записи, — только из-за точек, не попавших в файл (п. 7.4.9). `[N]`

7.8.2. Анализ ДОЛЖЕН работать для файлов GPX 1.0 и 1.1 сторонних программ с элементами `trk`/`trkseg`/`trkpt`; неизвестные элементы и расширения пропускаются. `[N]`

7.8.3. Анализ ДОЛЖЕН выполняться потоковым разбором с постоянным расходом RAM, не зависящим от размера файла. `[N]`

7.8.4. Прошивка ДОЛЖНА показывать отрезки по расстоянию `SPLIT_M` (время, темп, набор высоты каждого отрезка) и профиль высоты по расстоянию, сжатый до ширины экрана. `[N]`

7.8.5. Сохранённый трек ДОЛЖЕН выводиться на карту (п. 7.5.11) и МОЖЕТ использоваться как маршрут следования (п. 7.6.2). `[N]`

### 7.9. Интерфейс пользователя

7.9.1. Интерфейс ДОЛЖЕН состоять из экранов: карта, данные (показатели), навигация, спутники и состояние, меню (треки, карты, маршруты, путевые точки, настройки). `[N]`

7.9.2. Все функции ДОЛЖНЫ быть доступны с `KEYS_MIN` кнопками (предварительно 4: «вверх», «вниз», «выбор/старт», «назад») с короткими и длинными нажатиями; раскладка — вопрос 13.2.4. `[N]`

7.9.3. Нажатие ДОЛЖНО фильтроваться от дребезга (`KEY_DEBOUNCE_MS`); длинным считается нажатие не короче `LONG_PRESS_MS`. `[N]`

7.9.4. Отклик на нажатие (изменение на экране) ДОЛЖЕН быть не позднее `UI_RESPONSE_MS`, кроме перерисовки карты (п. 9.2.3), во время которой показывается признак обновления. `[N]`

7.9.5. Состояние записи, наличие решения GNSS и заряд ДОЛЖНЫ быть видны на каждом экране. `[N]`

7.9.6. Тексты интерфейса ДОЛЖНЫ быть на русском языке; шрифт содержит кириллицу и латиницу. `[N]`

### 7.10. Питание

7.10.1. Прошивка ДОЛЖНА показывать уровень заряда аккумулятора в процентах; способ измерения зависит от схемы питания (вопрос 13.2.5). `[N]`

7.10.2. Подсветка экрана (если есть) ДОЛЖНА гаснуть после бездействия `BACKLIGHT_TIMEOUT_S` (настраивается) и включаться любым нажатием. `[N]`

7.10.3. При заряде ниже `BATT_LOW_PCT` ДОЛЖНО выдаваться предупреждение; при напряжении ниже `BATT_CRITICAL` идущая запись сохраняется (п. 7.4.8), файлы закрываются, прошивка переходит в режим минимального потребления. `[N]`

7.10.4. Выключение пользователем ДОЛЖНО выполняться длинным нажатием с подтверждением; перед выключением сохраняется запись и закрываются файлы. `[N]`

### 7.11. Ошибки и диагностика

7.11.1. Каждая операция бизнес-логики, которая может завершиться отказом, ДОЛЖНА возвращать код состояния из общего перечисления (`Ok`, `StorageError`, `StorageFull`, `JnxBadVersion`, `JnxBadBounds`, `JnxBadLevels`, `JpegUnsupported`, `GpxParseError` и т. д.); исключения C++ не используются (вопрос 13.2.18). `[N]`

7.11.2. Экран состояния ДОЛЖЕН показывать: версию и профиль, состояние накопителя и свободное место, состояние приёмника, число найденных и отклонённых карт, счётчики ошибок (`nmea_bad_checksum`, `nmea_too_long`, `jnx_bad_tiles`, `jpeg_errors`, `track_points_lost`). `[N]`

7.11.3. Счётчики ошибок и состояние записи ДОЛЖНЫ быть глобальными объектами с постоянными именами, читаемыми из GDB без остановки логики: на них опираются DDTT-сценарии (п. 8.7.3). `[N]`

7.11.4. Прошивка НЕ ДОЛЖНА содержать кода, нужного только для тестов (тестовых команд, ловушек, флагов). `[N]`

### 7.12. Настройки

7.12.1. Настройки ДОЛЖНЫ сохраняться между включениями: интервал записи, поля экрана данных, смещение времени, единицы, включённые карты, ориентация карты, тайм-аут подсветки, признак незавершённого трека. Место хранения — вопрос 13.2.15. `[N]`

7.12.2. Хранилище настроек ДОЛЖНО содержать версию формата; при неизвестной версии или повреждении применяются значения по умолчанию, пользователь видит сообщение. `[N]`

7.12.3. Запись настроек ДОЛЖНА быть атомарной: после потери питания остаются прежние или новые настройки целиком. `[N]`

## 8. Требования к интерфейсам

### 8.1. Слой платы

8.1.1. Бизнес-логика ДОЛЖНА обращаться к оборудованию только через интерфейсы слоя платы: экран (п. 8.2), поток байтов приёмника (п. 8.3), файловая система (п. 8.4), кнопки (п. 8.5), питание (п. 8.6), часы, монотонное время в миллисекундах, журнал (п. 8.7). `[N]`

8.1.2. Исходники бизнес-логики НЕ ДОЛЖНЫ включать заголовки CMSIS, HAL, LL, CubeMX и драйверов конкретной периферии. Проверяется сборкой бизнес-логики для ПК (п. 9.4.2). `[N]`

8.1.3. Для каждого интерфейса п. 8.1.1 ДОЛЖНА существовать подмена для ПК, позволяющая тестировать бизнес-логику без платы (файлы на диске ПК, поток NMEA из записи, экран в памяти). `[N]`

8.1.4. Слой платы ДОЛЖЕН инициализироваться кодом, сгенерированным STM32CubeMX из `.ioc` профиля; ручные изменения сгенерированных файлов допускаются только в пользовательских секциях CubeMX. `[N]`

### 8.2. Экран

8.2.1. Интерфейс экрана ДОЛЖЕН предоставлять: размеры в точках, формат цвета, вывод прямоугольника точек в заданное окно экрана (для `F411CE` — без кадрового буфера), управление подсветкой (если есть). `[N]`

8.2.2. Вывод на экран СЛЕДУЕТ выполнять по DMA, чтобы декодирование следующей полосы шло параллельно выводу предыдущей. `[N]`

8.2.3. Модель экрана, размер и цветность — вопрос 13.2.1. Для растровых карт JNX экран ДОЛЖЕН быть цветным не менее 8 цветов (допущение 13.1.4); при монохромном экране карта выводится с дизерингом. `[N]`

### 8.3. Приёмник GNSS

8.3.1. Интерфейс приёмника ДОЛЖЕН предоставлять поток принятых байтов UART (кольцевой буфер, заполняемый DMA) и отправку команд настройки. `[N]`

8.3.2. Слой платы ДОЛЖЕН управлять питанием приёмника (включение, выключение, режим резервного питания часов приёмника), если схема это позволяет (вопрос 13.2.2). `[N]`

8.3.3. Выход PPS приёмника МОЖЕТ использоваться для подстройки часов; в ревизии 1.0 не обязателен. `[N]`

### 8.4. Накопитель и файловая система

8.4.1. Файловая система ДОЛЖНА поддерживать FAT32 на картах microSD SDHC; поддержка exFAT — вопрос 13.2.3. `[N]`

8.4.2. Интерфейс файловой системы ДОЛЖЕН предоставлять: открытие, чтение, запись, позиционирование, усечение, синхронизацию, переименование, удаление, перечисление каталога, свободное место, размер и время изменения файла. `[N]`

8.4.3. Каталоги на накопителе ДОЛЖНЫ быть: `MAP_DIR` — карты JNX; `TRACK_DIR` — записанные треки; `ROUTE_DIR` — маршруты следования; `CACHE_DIR` — служебные индексы. Отсутствующие каталоги создаются при запуске. Имена — вопрос 13.2.14. `[N]`

8.4.4. Подключение накопителя (SDIO/SDMMC 4 бит или SPI) — вопрос 13.2.3; бизнес-логика от него не зависит. `[N]`

### 8.5. Кнопки

8.5.1. Интерфейс кнопок ДОЛЖЕН выдавать события «нажата», «отпущена» с идентификатором кнопки и временем; распознавание короткого и длинного нажатия выполняет бизнес-логика (п. 7.9.3). `[N]`

8.5.2. Нажатие любой кнопки ДОЛЖНО выводить MCU из режима пониженного потребления. `[N]`

### 8.6. Питание

8.6.1. Интерфейс питания ДОЛЖЕН предоставлять напряжение аккумулятора в милливольтах, признак внешнего питания или зарядки и, если есть, уровень заряда от датчика (вопрос 13.2.5). `[N]`

### 8.7. Журнал и диагностика

8.7.1. Журнал ДОЛЖЕН выводиться через канал, не занимающий UART приёмника (SEGGER RTT, SWO или отдельный UART — вопрос 13.2.25); в сборке Release журнал МОЖЕТ отключаться. `[N]`

8.7.2. Прошивка ДОЛЖНА работать без подключённого отладчика и без читателя журнала. `[N]`

8.7.3. Проверки на плате ДОЛЖНЫ выполняться DDTT-сценариями stm32-gdbtest (подмодуль `modules/stm32-gdbtest`) по именам из ELF, без тестового кода в прошивке (п. 7.11.4). `[N]`

### 8.8. Сборка

8.8.1. Сборка ДОЛЖНА выполняться CMake с модулями stm32-cmake и stm32-cmake-yml, подключёнными git-подмодулями в `modules/` с закреплённым коммитом (п. 1.5.7). `[N]`

8.8.2. Выбор профиля ДОЛЖЕН выполняться пресетами CMake (`CMakePresets.json`) через `STM32_YML_PROFILE`; общая конфигурация — `stm32_config.toml` (или `.yml`) в корне, профили плат — `boards/<профиль>.toml`. `[N]`

8.8.3. Бизнес-логика ДОЛЖНА собираться отдельной библиотекой, общей для обоих профилей и для сборки на ПК. `[N]`

8.8.4. Каждая сборка ДОЛЖНА выдавать ELF, HEX, BIN и карту компоновки; версия прошивки берётся из одного места и попадает в образ, заставку и атрибут `creator` (п. 6.1.3). `[N]`

8.8.5. CI ДОЛЖЕН собирать оба профиля и выполнять тесты бизнес-логики на ПК; CI не заменяет проверку на плате. Состав CI — вопрос 13.2.25. `[N]`

### 8.9. Внешние программы

8.9.1. Файлы GPX прошивки ДОЛЖНЫ открываться без ошибок в GPXSee и проходить проверку по схеме GPX 1.1 (`xmllint --schema`). `[N]`

8.9.2. Прошивка ДОЛЖНА читать файлы JNX, созданные хотя бы одной распространённой программой подготовки карт; какие программы и файлы используются для приёмки — вопрос 13.2.21. `[N]`

## 9. Нефункциональные требования

### 9.1. Память

9.1.1. После завершения запуска (п. 7.1.1) прошивка НЕ ДОЛЖНА выделять динамическую память (`malloc`, `new`); буферы размещаются статически. `[N]`

9.1.2. Только `F411CE`: статически размещённые данные (`.data`, `.bss`) вместе с зарезервированным стеком ДОЛЖНЫ занимать не более `RAM_USE_MAX_PCT` от 128 КиБ. Подтверждается картой компоновки. `[N]`

9.1.3. Образ прошивки каждого профиля ДОЛЖЕН занимать не более `FLASH_USE_MAX_PCT` от Flash MCU; шрифты и изображения интерфейса входят в образ. `[N]`

9.1.4. Максимальная глубина стека ДОЛЖНА подтверждаться анализом (`-fstack-usage`) или замером заполнения стека на плате с запасом не менее 25 %. `[N]`

### 9.2. Быстродействие

9.2.1. Разбор NMEA и обновление показателей ДОЛЖНЫ успевать за поток приёмника при `NAV_RATE_HZ` без роста очереди байтов. `[N]`

9.2.2. Запись точки в буфер ДОЛЖНА занимать не более 1 мс; сброс буфера на накопитель НЕ ДОЛЖЕН задерживать приём NMEA (п. 9.2.1). `[N]`

9.2.3. Полная перерисовка окна карты с тайлами JNX ДОЛЖНА занимать не более `MAP_REDRAW_F411_MS` на `F411CE` и `MAP_REDRAW_H723_MS` на `H723VG` для экрана, выбранного по вопросу 13.2.1, и тайлов размером 256×256 точек. Подтверждается замером на плате. `[N]`

9.2.4. Поиск тайлов окна карты (без декодирования) ДОЛЖЕН занимать не более 50 мс при `JNX_TEST_TILES` тайлах на уровне. `[N]`

### 9.3. Надёжность

9.3.1. Потеря питания в любой момент НЕ ДОЛЖНА приводить к потере ранее сохранённых треков, настроек и путевых точек, а для идущей записи — к потере точек, сброшенных на накопитель (п. 6.3.1, 7.4.8). Проверяется сериями отключений питания на плате (TC-25). `[N]`

9.3.2. Повреждённые или неожиданные данные во входных файлах (JNX, GPX) и в потоке NMEA НЕ ДОЛЖНЫ приводить к зависанию, выходу за границы буферов или сбросу MCU: все длины и смещения проверяются до использования. `[N]`

9.3.3. Сторожевой таймер ДОЛЖЕН быть включён в Release-сборке; самая длинная операция (перерисовка карты, построение индекса) ДОЛЖНА сбрасывать его по ходу работы. `[N]`

### 9.4. Переносимость

9.4.1. Бизнес-логика ДОЛЖНА давать одинаковые результаты на ПК и на обоих MCU: координаты и расстояния вычисляются в целых числах или в `double` с одинаковыми правилами округления; вывод чисел в GPX не зависит от реализации `printf`. `[N]`

9.4.2. Бизнес-логика ДОЛЖНА собираться на ПК компиляторами GCC и Clang без предупреждений с `-Wall -Wextra`. `[N]`

### 9.5. Энергопотребление

9.5.1. Время работы от аккумулятора в режиме записи с картой и ток в режиме минимального потребления ДОЛЖНЫ быть заданы после выбора схемы питания (вопрос 13.2.5) и подтверждены замером. В ревизии 1.0 целевые значения не заданы. `[N]`

9.5.2. В паузах между событиями MCU ДОЛЖЕН находиться в режиме ожидания прерывания (`WFI`). `[N]`

### 9.6. Сопровождаемость

9.6.1. Каждое требование ДОЛЖНО быть прослеживаемо до кода и проверки (раздел 12, приложение D). `[N]`

9.6.2. Исходники ДОЛЖНЫ форматироваться по `.clang-format` репозитория; сгенерированный CubeMX код и подмодули не форматируются. `[N]`

### 9.7. Лицензии

9.7.1. Репозиторий распространяется по MIT; код под GPL (в том числе GPXSee) НЕ ДОЛЖЕН включаться в репозиторий и образ. `[N]`

9.7.2. Сторонние библиотеки (декодер JPEG, файловая система и т. п.) ДОЛЖНЫ иметь лицензию, совместимую с MIT, и перечисляться в README с версией и лицензией. Выбор — вопрос 13.2.7. `[N]`

9.7.3. Тестовые карты и треки в репозитории ДОЛЖНЫ быть созданы в проекте (синтетические) или иметь лицензию, разрешающую распространение; размер каждого файла — не более `TEST_FILE_MAX`. `[N]`

## 10. Совместимость и эволюция

10.1. Формат GPX: прошивка пишет только GPX 1.1 по разделу 6; изменение формата записи (например, добавление расширений по вопросу 13.2.12) оформляется новой ревизией и сохраняет читаемость файлов в GPXSee. `[N]`

10.2. Формат JNX: поддержка версий, кроме 3 и 4, добавляется новой ревизией после сверки с описанием и образцами файлов. `[N]`

10.3. Хранилище настроек и индексы тайлов имеют номер версии формата (п. 5.6.2, 7.12.2); при изменении формата номер увеличивается, старые данные отбрасываются без отказа прошивки. `[N]`

10.4. Новая плата добавляется новым профилем (`boards/<профиль>.toml`, `.ioc`, слой платы) без изменения бизнес-логики; если функции не помещаются в ресурсы платы, таблица п. 3.3.1 дополняется новой ревизией. `[N]`

10.5. Обновление закреплённых коммитов подмодулей (`modules/`) и копий навыков (`skills/`) выполняется отдельной задачей с записью в CHANGELOG и проверкой сборки обоих профилей. `[N]`

## 13. Допущения и открытые вопросы

### 13.1. Допущения

13.1.1. Внутри тайла JNX пиксели линейно соответствуют широте и долготе (равнопромежуточная проекция). Зависят пп. 5.4.3, 7.5.4; проверяется TC-27 и TC-51 на реальных файлах.

13.1.2. Размер файла JNX не превышает 4 ГиБ − 1 байт: смещения в формате 32-битные. Поэтому FAT32 достаточно для карт (п. 8.4.1).

13.1.3. Приёмник выдаёт NMEA 0183 версии 4.x с идентификатором `GN` для совместного решения. Зависят пп. 7.2.3, 7.2.4.

13.1.4. Экран цветной, не менее 128×128 точек; для растровых карт этого достаточно. Зависят пп. 8.2.3, 9.2.3.

13.1.5. Прототип собирается из готовых модулей на макетной плате или переходной плате; корпус, влагозащита и сертификация не требуются.

13.1.6. Плата `H723VG` используется с собственным экраном ST7735 только для первых опытов; экран навигатора выбирается по вопросу 13.2.1.

## Приложение B. Раскладка файла JNX (информативно)

Нормативные правила — раздел 5. Поля с пометкой «?» не используются прошивкой и подлежат сверке с описанием (вопрос 13.2.26).

```text
Заголовок (little-endian)
0x00  uint32  версия (3 | 4)
0x04  uint32  серийный номер устройства (?)
0x08  int32   север   ┐
0x0C  int32   восток  │ границы карты, единицы 180/0x7FFFFFFF градуса
0x10  int32   юг      │
0x14  int32   запад   ┘
0x18  uint32  число уровней N
0x1C  20 байт срок действия, ID продукта, CRC, версия и смещение подписи (?)
0x30  uint32  Z-порядок                          — только версия 4

Таблица уровней: с 0x30 (v3) или 0x34 (v4), N записей
  v3: uint32 число тайлов | uint32 смещение таблицы тайлов | uint32 масштаб      (12 байт)
  v4: то же + uint32 (?) + строка авторских прав, завершённая 0x00             (переменная)

Блок метаданных карты (?)                        — после таблицы уровней

Таблица тайлов уровня: по смещению из записи уровня, записи по 28 байт
  int32 север | int32 восток | int32 юг | int32 запад
  uint16 ширина | uint16 высота | uint32 размер данных | uint32 смещение данных

Данные тайла: JPEG без маркера SOI (FF D8): перед декодированием SOI восстанавливается

Конец файла: подпись (?)
```

## Приложение D. Соглашение о ссылках на ТЗ из кода

D.1. Ссылка на требование оформляется однострочным комментарием рядом с реализацией: `// ТЗ 7.4.8`. Для нескольких требований — перечисление через запятую: `// ТЗ 5.4.1, 5.4.2`.

D.2. Для тестов используется идентификатор тест-кейса и номера проверяемых требований: `// TC-15: ТЗ 6.2.1, 9.4.1`.

D.3. Пример:

```cpp
// ТЗ 5.1.3: поддерживаются версии 3 и 4.
if ( version != 3 && version != 4 )
{
    return Status::JnxBadVersion;
}
```

D.4. При исключении требования его номер сохраняется с пометкой «(исключено)» (п. 1.6.2); комментарий в коде удаляется вместе с реализацией.
