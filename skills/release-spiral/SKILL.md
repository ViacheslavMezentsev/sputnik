# Спираль выпуска

Навык собирает документ о том, как проект дошёл от одного выпуска до другого: витки работы по порядку, где шла
проверка, сколько времени ушло на каждую задачу и где были петли «сбой → правка → повтор». Спираль не привязана
к методике: основа — дисциплина git (ветки, MR, теги, типы коммитов) и журналы CI. Журналы проверки на цели
(stm32-gdbtest, стенды) делают сектор проверки измеренным, а не оценённым.

## 1. Порядок работы

1. **Границы.** Предыдущий и текущий тег (или коммиты этапа), интеграционная ветка (линия, куда сливаются
   рабочие ветки), основная ветка, следующий выпуск — для подписи «план …».
2. **События.** Найти источники по [event-sources.md](references/event-sources.md) и собрать журнал:

   ```bash
   python3 scripts/collect_events.py --repo . --range v1.2.0..v1.3.0 --out build/spiral/events.jsonl \
       --hil-runs 'build/*-hil/hwtest/runs' --bridge-results ../bridge/results --bridge-repo app \
       --local-ci 'build/local-ci-*' --local-tz +05:00 --recordings recordings.csv --manual manual.csv
   ```

   Что нельзя найти в файлах (лаборатория, ручной замер, смена платы), — в `manual.csv` и `recordings.csv`
   со временем начала и конца; спросить у владельца, если записей нет.
3. **Черновик витков** по правилам [rules.md](references/rules.md):

   ```bash
   python3 scripts/build_turns.py build/spiral/events.jsonl --line release/1.x --versions 1.2.0,1.3.0,1.4.0 \
       --out build/spiral/turns.json
   ```

4. **Правка черновика агентом** (обязательно): названия витков по смыслу, «результат» и абзац `notes`,
   склейка или разделение витков, задачи без журнала (ТЗ, изменения, разбор) с `"src": "est"`, смена платы,
   стенды (`"stands"`), выводы (`"conclusions"`), что не учтено (`"not_included"`), источники (`"sources"`).
   Время из журналов не править; оценки помечать.
5. **Документ** по макету [document.md](references/document.md):

   ```bash
   python3 scripts/render_spiral.py build/spiral/turns.json --events build/spiral/events.jsonl \
       --out "build/spiral/Спираль_выпуска_1.3.0.pdf" --project "<изделие>" --tz +05:00
   ```

6. **Проверка.** Просмотреть страницы (подписи, наложения на рисунках), сверить итоги с журналами, назвать
   владельцу, что из журналов, а что оценено.

## 2. Правила по умолчанию

| Что | По умолчанию | Где менять |
| --- | --- | --- |
| Спираль 1 | от предыдущего тега до тега выпуска | `--range` |
| Спираль 2 | события после тега (проверки выпуска), витки по перерыву 12 ч | `confirm_gap_h` |
| Виток | ветка, слитая в линию; внутри ветки — до коммита проверки (`test…`), за которым идёт не проверка; прямые коммиты в линию — по перерыву 24 ч | `--no-split-on-check`, `direct_commit_gap_h` |
| Событие → виток | первый виток, закончившийся после события | правка `turns.json` |
| Направление | против часовой стрелки от верхней точки: план и ТЗ → изменение → проверка → CI и выпуск | — |
| Сектор коммита | `docs(spec/todo/plan)` — план; `feat/fix/refactor/style/build` — изменение; `test` — проверка; `ci/chore`, CHANGELOG, слияния — выпуск | `commit_types` в `rules.json` |
| Время прогона | машинное + 3 мин на запуск, + 10 мин на сбой; смена платы 5 мин | `time` в `rules.json` |
| CI сервера | ветка, MR или слияние — 10 мин, тег — 15, образ — 15 (оценка, если нет журнала) | `time` |
| Изменения и документы | занятость между коммитами (окно 30 мин до коммита, промежутки до 45 мин) — оценка | правка задач |
| Календарь | коммит 30 мин, слияние 10, локальный CI 10, прогоны и записи — по длительности | `time` |

Свои правила — копия `scripts/rules.json` с изменёнными ключами в `--rules`.

## 3. Чего не делать

- Не выдавать оценку за факт: у каждой задачи `src` — `fact` (журнал) или `est` (оценка).
- Не считать прогоны дважды: прогоны stm32-gdbtest внутри задания моста считаются по заданию.
- Не угадывать события: нет журнала — нет события; пробел называется в разделе «Что не учтено».
- В документах для публикации — без серийных номеров, адресов, личных путей и названий закрытых проектов.
